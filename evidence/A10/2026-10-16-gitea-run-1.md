## Review notes

1. GT-01 returned 404 for an authenticated user, not 401. The refusal comes from the team permissions, not from a failed login. GT-02, with the same request by a developer, returned 200.
2. GT-03: the push was refused by Gitea with the message "protected branch main", not by a network or authentication error.
3. GT-04: the expected HTTP code was not known before this run; the test only required a refusal and checked separately that the pull request was not merged. Gitea 1.23.8 returns 405. The test can now require 405 exactly; any change will be recorded in the test's history.
4. GT-06 shows the controls do not block normal work: an approved change is merged.

## What this evidence shows and does not show

It shows that, in the lab on the date above, the Gitea setup in `lab/gitea` keeps the repository away from the support team, refuses direct pushes to `main`, blocks merges without approval, refuses self-approval, and lets an approved change through.

It does not show who can change the branch protection rule (an administrator can), it does not test login through Keycloak, and it does not test automated security tests in the pipeline (8.29, still planned). The SoA status of the controls is not changed, because Lagune Payroll is fictional.
